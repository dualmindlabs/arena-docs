Sending the same prompt to two models and collecting a vote sounds simple. Underneath are design problems that, left unsolved, make every result meaningless. This page explains the reasoning behind each choice.

## Fair comparison is a design problem

A comparison is only valid when:

- both models receive **the exact same input**, built the same way,
- both run under **the same constraints** (token limit, temperature, timeout),
- the person voting **doesn't know which model wrote which answer**, and
- results are **aggregated across many comparisons**, not read from one exchange.

Any deviation adds a bias that compounds over time, which is why the Arena was built around these constraints rather than adding them later.

## Why blind comparison comes first

When you know which model you're reading, familiar biases switch on:

- **Brand familiarity**: a well-known model feels more authoritative, whatever it wrote.
- **Expectation**: a model known for code gets extra credit on everything else.
- <Tooltip headline="Anchoring" tip="A cognitive bias where the first piece of information you see sets the reference point for everything after it.">**Anchoring**</Tooltip>: the first answer you read becomes the yardstick for the second.

In Battle mode the Arena labels answers **Model A** and **Model B** and reveals the names only after your vote. With identities hidden, crowd votes become a useful signal: published arena research found crowd votes agreed with expert raters roughly 72 to 83 percent of the time ([Chiang et al., 2024](https://arxiv.org/abs/2403.04132)).

## Prompt bias is real

Not every prompt is an equally good test:

- long, multi-part reasoning favours models with larger context windows,
- chatty prompts favour chat-tuned models,
- code prompts favour models trained heavily on code, and
- one-word completions barely separate models at all.

Random pairing selects models without knowing the prompt, but users choose their own prompts, so a developer-heavy crowd skews toward code. No system removes prompt bias entirely; the goal is to keep it **proportional and visible** rather than hidden. Category leaderboards on the [roadmap](/roadmap) are the next step.

## Latency is not intelligence

A 200 ms answer and a 4 s answer aren't comparable on quality without isolating speed:

1. **Speed shapes perception.** A fast answer feels fluent before you've read it; a slow one gives you longer to find fault.
2. **Speed is partly hosting.** The same model can be fast or slow depending on where and how it's served.

So the Arena generates both answers in parallel, shows them together, and records response time separately. Details: [Latency and speed](/concepts/latency-measurement).

## Rankings need volume

A model with 12 wins from 20 battles means something different from one with 1,200 wins from 2,000, even at the same win rate. That's why the leaderboard leads with ELO rather than raw win counts, and why every entry shows its battle count. Votes are timestamped and tied to a comparison, so rating changes can be traced over time.

## What skipping each principle costs

| If you skip... | You get... |
| :-- | :-- |
| Blind comparison | Votes on brand, not output |
| Identical inputs | Apples-to-oranges prompting |
| Separating latency | Hosting quality posing as intelligence |
| ELO over win rate | Small-sample flukes that look like rankings |
| Traceable votes | A leaderboard that drifts without explanation |
