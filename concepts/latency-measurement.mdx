Speed matters when you pick a model for a product, but it shouldn't decide which answer is **better**. DualMind records speed and token usage, and keeps both out of the ranking.

## What is recorded

<ResponseField name="responseTimeMs" type="integer">
  Wall-clock time of the request in milliseconds, measured by the API. In a battle both models run in parallel, so this is the time until **both** answers were ready.
</ResponseField>
<ResponseField name="usage" type="object">
  Token counts reported by the provider.

  <Expandable title="properties">
    <ResponseField name="promptTokens" type="integer">Tokens in your prompt and system prompt.</ResponseField>
    <ResponseField name="completionTokens" type="integer">Tokens the model generated.</ResponseField>
    <ResponseField name="totalTokens" type="integer">The sum of both.</ResponseField>
  </Expandable>
</ResponseField>
<ResponseField name="model1TimeMs / model2TimeMs" type="integer">
  The response time stored with each turn of a [thread](/concepts/threads).
</ResponseField>

<Note>
  Time to first token and tokens per second aren't reported yet. Use the [streaming endpoint](/api-reference/guides/streaming) if you want to measure them yourself.
</Note>

## Keeping speed out of the vote

<CardGroup cols={2}>
  <Card title="Parallel generation" icon="git-compare-arrows">
    Both models get the prompt at the same moment, under the same limits.
  </Card>
  <Card title="Shown together" icon="columns-2">
    Battle answers appear side by side once both are ready, so a faster model doesn't get read first.
  </Card>
  <Card title="Not part of ELO" icon="trophy">
    The leaderboard only counts votes. Speed never adds or removes points.
  </Card>
  <Card title="Same settings" icon="sliders-horizontal">
    Same `maxTokens` (4096 by default) and `temperature` (0.7) for both sides.
  </Card>
</CardGroup>

## Why speed and quality are kept apart

A fast answer feels fluent before you've read a word, and a slow one gives you more time to spot flaws. Speed also depends on where a model is hosted and how busy the provider is, not only on the model. Folding it into quality would make the leaderboard partly a hosting benchmark.

## Measure it yourself

<CodeGroup>
```javascript measure.mjs {8-13}
const t0 = performance.now();
const res = await fetch("{{apiBase}}/api/arena/chat/stream", {
  method: "POST",
  headers: { Authorization: `Bearer ${token}`, "Content-Type": "application/json" },
  body: JSON.stringify({ prompt: "Summarise the plot of Hamlet in three lines", model: "llama-3.1-8b-instant" }),
});
if (!res.ok) throw new Error(`HTTP ${res.status}`);
const reader = res.body.getReader();
let first = null;
for (;;) {
  const { done } = await reader.read();
  if (done) break;
  first ??= performance.now() - t0; // time to first chunk
}
console.log({ timeToFirstChunkMs: Math.round(first), totalMs: Math.round(performance.now() - t0) });
```

```python measure.py {12-14}
import time, requests

t0 = time.perf_counter()
first = None
with requests.post(
    "{{apiBase}}/api/arena/chat/stream",
    headers={"Authorization": f"Bearer {token}"},
    json={"prompt": "Summarise the plot of Hamlet in three lines", "model": "llama-3.1-8b-instant"},
    stream=True,
    timeout=120,
) as r:
    r.raise_for_status()
    for chunk in r.iter_content(chunk_size=None):
        if first is None:
            first = time.perf_counter() - t0
print({"time_to_first_chunk_s": round(first, 3), "total_s": round(time.perf_counter() - t0, 3)})
```
